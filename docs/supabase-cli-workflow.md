# Supabase CLI Workflow

This project uses Supabase CLI as the migration runner, alongside Drizzle for
schema authoring and migration generation. See
`docs/database-audit-and-plan.md` sections 1 and 11 for the rationale.

## Generating migrations

1. Edit the Drizzle schema under `packages/db/src/schema/`.
2. Run `pnpm db:generate` to produce a new SQL migration via `drizzle-kit`.
3. Copy (or move) the generated `.sql` file from
   `packages/db/src/migrations/` into `supabase/migrations/`, renaming it to
   follow the Supabase timestamp convention (`YYYYMMDDHHMMSS_description.sql`).
4. Review the SQL, add any RLS policies, grants, or data backfills that
   Drizzle cannot express, then commit.

## Applying migrations

- **Local development:** `supabase db reset` reapplies the full migration
  history on top of a clean local database and runs `supabase/seed.sql`.
- **Staging / production:** `supabase db push` applies any pending
  migrations to the linked remote project. This is the canonical deploy path.
- **Dry run:** `supabase db push --dry-run` prints the SQL that would be
  executed without touching the remote.

## Drift detection in CI

The `ci.yml` workflow runs `drizzle-kit` in diff mode against a freshly
migrated shadow database. If the committed migrations do not reproduce the
current Drizzle schema, the job fails. This guarantees that
`supabase/migrations/` stays in sync with `packages/db/src/schema/`.

## Linking a remote project

Before the first `db push` from a new machine, link the CLI to the remote
project:

```bash
supabase login
supabase link --project-ref <project-ref>
```

To import changes made directly in the Supabase dashboard (hotfixes, new
roles, etc.), use:

```bash
supabase db pull
```

This writes a new timestamped migration under `supabase/migrations/` that
captures the remote diff. Review and commit it so the Drizzle schema can be
updated to match.

## Coexistence with `packages/db/src/migrations/`

During the transition both directories will exist:

- `packages/db/src/migrations/` remains the **source generated by Drizzle**.
  Do not delete it. It is still consumed by the existing Node runners and
  drift checks.
- `supabase/migrations/` is the **source of truth applied by Supabase CLI**.
  Migrations here may include hand-written RLS and policies not emitted by
  Drizzle.

Once the CLI migration path is proven in staging, a follow-up task will
collapse these into a single directory. Until then, every new migration
must be mirrored into both locations.
